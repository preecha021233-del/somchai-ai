# SOMCHAI AI

**Self-Evolving Modular AI Agent — Protected Core + Sandboxed Plugins**

SOMCHAI AI is an Android personal assistant being developed toward an independent, self-evolving system. Its long-term architecture is governed by `docs/IMPLEMENTATION_PLAN.md` (Master Command).

## Current implemented baseline

- Android app foundation using Kotlin, Jetpack Compose and Material 3.
- Offline-first chat UI routed through a deterministic internal rule engine by default.
- Optional OpenAI-compatible Chat Completions connector, invoked only with the explicit `/ai` command.
- API key encryption with Android Keystore (AES-GCM).
- Core permission allowlist and untrusted external-data boundary.
- Declarative plugin staging, validation, SHA-256-bound approval, activation and rollback.
- Built-in web search operation using DuckDuckGo Instant Answer API, invoked with `/search` after approval.
- Structured local memory with add, search, retrieval, deletion, backup and restore; production data is encrypted with AES-256-GCM using Android Keystore.
- Deterministic task decomposition for research, development, troubleshooting and general tasks.
- Append-oriented activity log for internal processing and memory events.
- Daily API request and local storage budgets.
- GitHub Actions build, unit tests and APK artifact upload.

**Phase 1 implementation limitation:** the internal processor remains a deterministic, bounded rule engine. A native llama.cpp on-device inference runtime and an explicit installer for the official Qwen2.5-0.5B-Instruct GGUF model have been added on `phase-1/local-brain-runtime`; this integration is pending CI and real-device testing. It is not yet evidence of advanced or human-level reasoning, and unsupported requests must not be silently sent to an external provider. Optional provider requests require the explicit `/ai` command and an owner-configured provider. Do not create accounts, API keys, subscriptions or charges without the owner's explicit approval.

The current JSON plugin system selects a finite set of operations already implemented by the app. It is not an arbitrary code execution runtime and is not yet the full self-extension system described in the Master Command.

## App update compatibility — mandatory and unchanged

Published updates must install directly over the existing SOMCHAI AI installation. Keep the application ID `com.somchai.ai` and the exact same owner-controlled signing keystore/certificate for every release. Increase `versionCode` with every published update. Do not uninstall the old app or clear its data to work around a signing mismatch.

The owner-signed release workflow is manual-only and requires these GitHub Actions secrets:
- `SOMCHAI_SIGNING_KEYSTORE_BASE64` — base64-encoded original owner keystore file
- `SOMCHAI_SIGNING_STORE_PASSWORD`
- `SOMCHAI_SIGNING_KEY_ALIAS`
- `SOMCHAI_SIGNING_KEY_PASSWORD`
- `SOMCHAI_SIGNING_CERT_SHA256` — SHA-256 fingerprint of the original installed/release app signing certificate (hex, colons optional)

Never commit the keystore or passwords, and never paste them into chat or logs. The workflow restores the keystore only on the ephemeral runner, builds a Release APK, and verifies the package ID, expected versionCode and certificate fingerprint before uploading `somchai-owner-signed-release`. If a required secret is missing or the certificate differs, the release job fails closed. Debug APKs use a different application ID and are not a supported update channel.

Before installing/publishing an update, verify the installed app's actual versionCode and signing certificate, then test installing the owner-signed APK over the existing app on the target device while preserving user data. A signature or application-ID mismatch blocks release. Never replace the owner's signing key as an update workaround.

## Security boundary

The current agent does not execute arbitrary downloaded Kotlin, shell commands, APKs or JavaScript. Plugins are JSON manifests selecting a finite core-owned operation. The Protected Core is protected from agent modification by application packaging and release signing, not by a folder name alone. Internet results and model output are untrusted data. Android's app sandbox does not make in-process plugin code a strong OS isolation boundary.

## Build

GitHub Actions runs JVM tests and builds the ARM64 Debug and instrumentation APKs on normal CI events. A manual workflow dispatch also runs the owner-signed Release build, but only when the original signing secrets above are configured and validated. The release artifact is not considered device-accepted until an in-place update test confirms the existing app's data is preserved. Android SDK API 35 is used.

For local Android Studio use, open the repository as a Gradle project and use a locally installed Gradle 8.9 or generate a wrapper with: `gradle wrapper --gradle-version 8.9`.

## Setup

1. Install the owner-signed release APK for normal use and future in-place updates.
2. Internal supported commands work without an external AI provider. An optional provider is called only when the owner explicitly uses `/ai` and has configured the provider. No provider, account, API key or paid service is mandatory.
3. To use the currently implemented web-search operation, approve the staged Web Search plugin in Plugins and use `/search` followed by a query.
4. Use `/remember text`, `/recall query`, and `/forget id` for local memory. The Memory tab also supports adding, searching and deleting stored entries.

## Master Command and development status

The authoritative requirements, owner-approval rules, Protected Core/Evolution Zone architecture, phase gates, internal processing goals and self-evolution roadmap are in [docs/IMPLEMENTATION_PLAN.md](docs/IMPLEMENTATION_PLAN.md).

Phase 0 is closed based on repository audit and owner device update testing. Phase 1 implementation is in progress. The local model runtime is under CI/device verification and is not yet accepted as a completed independent AI brain or a security-certified release. Remaining Phase 1 acceptance gates must be completed with automated and device evidence. Do not describe planned capabilities as implemented.

## Release limitations

DuckDuckGo Instant Answer is not exhaustive general web search. Device testing, owner signing-key setup, in-place upgrade verification, provider compatibility, encrypted backup, privacy disclosure, accessibility review and penetration testing remain release gates.

# PART 1 — วิสัยทัศน์และเป้าหมาย

สร้าง SOMCHAI AI ให้เป็นระบบ AI ที่มีสมอง ระบบคิดวิเคราะห์ และความสามารถในการประมวลผลเป็นของตัวเอง สามารถค้นหาความรู้จากโลกออนไลน์ นำข้อมูลมาวิเคราะห์ และสร้างคำตอบด้วยระบบประมวลผลภายในของตนเอง

SOMCHAI ต้องทำงานในลักษณะ AI Assistant ที่สามารถสนทนา ตอบคำถาม ค้นคว้า และแก้ไขปัญหาได้ โดยไม่ใช้ AI ภายนอกเป็นสมองหลัก

ต้องแยกสถานะของทุกความสามารถให้ชัดเจน:
- ทำงานจริงและผ่านการทดสอบแล้ว
- มีอยู่แต่ยังไม่สมบูรณ์
- มีเพียงโครงสร้างหรือต้นแบบ
- อยู่ระหว่างพัฒนา
- เป็นแผนในอนาคต
- ยังทำไม่ได้หรือมีข้อจำกัดทางเทคนิค

ห้ามกล่าวอ้างว่าระบบทำงานได้แล้วหากไม่มีหลักฐานการทดสอบ

# PART 2 — สมองและระบบประมวลผลภายใน

SOMCHAI ต้องมีระบบประมวลผลและกลไกการทำงานภายใน ไม่ใช่เพียงแอปที่ส่งข้อความไปยัง AI ของบริษัทอื่นแล้วนำคำตอบกลับมาแสดง

ต้องพัฒนาความสามารถภายใน เช่น:
- Internal Processing
- Language Understanding
- Intent and Context Analysis
- Reasoning Workflow
- Task Planner และ Task Decomposition
- Decision Engine
- Tool Orchestration
- Result Verification
- Self-Evaluation
- Learning และ Skill Management

สมองหลักต้องเป็นระบบภายในของ SOMCHAI ต้องแยกให้ชัดระหว่างการประมวลผลตามกฎ การค้นหาข้อมูล การอนุมาน การสร้างภาษาด้วยโมเดล และการเรียนรู้จากการทดลอง ห้ามเรียกการทำงานตามเงื่อนไขธรรมดาว่าเป็นความฉลาดระดับมนุษย์

สามารถศึกษา On-device AI Model เพื่อเพิ่มความสามารถด้านภาษาและการให้เหตุผล โดยต้องทดสอบ RAM, CPU/GPU/NPU, ขนาดโมเดล, ความเร็ว, แบตเตอรี่, ความร้อน และข้อจำกัดของอุปกรณ์จริง

# PART 3 — อินเทอร์เน็ตและระบบค้นหาข้อมูล (Search Engine & Research)

SOMCHAI ต้องทำงานออนไลน์เพื่อค้นหาความรู้และข้อมูลจากอินเทอร์เน็ตในลักษณะ Search Engine โดยมีความสามารถมากกว่าการแสดงรายการเว็บไซต์

ความสามารถที่ต้องพัฒนา:
1. วิเคราะห์คำถามและระบุว่าต้องค้นหาข้อมูลอะไร
2. สร้างคำค้นที่เหมาะสม
3. ค้นหาข้อมูลจากเว็บไซต์และแหล่งข้อมูลหลายแห่ง
4. เข้าถึงและอ่านเนื้อหาจากเว็บไซต์และเอกสารที่เข้าถึงได้
5. ดึงข้อมูลที่เกี่ยวข้องกับคำถาม
6. เปรียบเทียบข้อมูลจากหลายแหล่ง
7. ตรวจสอบวันที่ ความน่าเชื่อถือ และความทันสมัย
8. แยกข้อเท็จจริง ความคิดเห็น และข้อมูลที่ยังไม่ยืนยัน
9. สรุปผลจากข้อมูลที่ตรวจสอบได้
10. แสดงชื่อแหล่งข้อมูล ลิงก์ และวันที่เมื่อมีข้อมูล
11. แจ้งอย่างตรงไปตรงมาเมื่อเว็บไซต์เข้าไม่ได้ ข้อมูลไม่พอ หรือแหล่งข้อมูลขัดแย้งกัน

การค้นหาออนไลน์เป็นเครื่องมือและช่องทางเข้าถึงความรู้ให้สมองภายใน ไม่ใช่การนำ AI ภายนอกมาแทนสมองของ SOMCHAI

ห้ามจำกัดระบบไว้เพียง Search API แบบสรุปคำตอบสั้น ๆ หากเป้าหมายงานต้องการอ่านหน้าเว็บจริง ต้องออกแบบ Web Reader และระบบดึงเนื้อหาที่เหมาะสมเพิ่มเติม

# PART 4 — กระบวนการตอบคำถามและค้นคว้า

เมื่อได้รับคำถาม SOMCHAI ต้อง:
1. ทำความเข้าใจภาษา เจตนา และบริบท
2. วิเคราะห์ว่าคำถามต้องใช้ข้อมูลประเภทใด
3. พิจารณาว่าควรค้นหาออนไลน์หรือใช้ความรู้และเครื่องมือภายใน
4. หากต้องค้น ให้ค้นจากแหล่งที่เกี่ยวข้องหลายแหล่งตามความเหมาะสม
5. อ่านและตรวจสอบเนื้อหาต้นทาง ไม่พึ่งเพียงชื่อหรือข้อความตัวอย่างจากผลค้นหา
6. เปรียบเทียบข้อมูลและตรวจสอบความขัดแย้ง
7. วิเคราะห์ด้วยระบบประมวลผลภายในของ SOMCHAI
8. สร้างคำตอบที่ตรงคำถาม เข้าใจง่าย และระบุข้อจำกัด
9. แสดงแหล่งอ้างอิงสำหรับข้อเท็จจริงที่ได้จากการค้นออนไลน์

ห้ามสร้างแหล่งอ้างอิง URL หรือข้อเท็จจริงขึ้นเอง หากตรวจสอบไม่ได้ต้องแจ้งว่าไม่สามารถยืนยันได้

# PART 5 — หลักการเรียนรู้และความจำ

**หลักการสำคัญ: รู้จักค้นหาความรู้ ไม่ใช่ต้องจดจำความรู้ทั้งหมด**

อะไรที่ค้นหาได้จากอินเทอร์เน็ต ไม่จำเป็นต้องเก็บเป็นความจำถาวร ให้เน้นพัฒนาวิธีคิด ทักษะ เครื่องมือ และประสบการณ์ มากกว่าการสะสมข้อมูลดิบ

- ไม่เก็บข้อมูลทุกอย่างที่ค้นพบจากอินเทอร์เน็ตเป็นความจำถาวร
- ข้อมูลค้นคว้าทั่วไปให้ใช้ในบริบทของงานปัจจุบัน และทิ้งได้เมื่อไม่จำเป็น
- ค้นหาข้อมูลใหม่ได้เมื่อต้องการ แทนการพยายามจดจำข้อมูลที่เปลี่ยนแปลงตลอดเวลา
- เก็บเฉพาะวิธีคิด ทักษะ ขั้นตอนที่ผ่านการทดสอบ บทเรียน และข้อมูลที่เจ้าของอนุญาตหรือจำเป็นต่อการทำงาน
- แยก Working Memory, ประสบการณ์, Skill Memory และ Owner Memory ออกจากข้อมูลชั่วคราวจากการค้นเว็บ
- ต้องมีระบบค้นคืน ตรวจสอบ ปรับปรุง ส่งออก และลบความจำ
- ห้ามเก็บข้อมูลจากเว็บทั้งหมดโดยอัตโนมัติ

# PART 6 — AI ภายนอกและข้อจำกัดการใช้งาน

ห้ามบังคับเชื่อมต่อ OpenAI, Gemini, Claude หรือ AI Provider อื่นให้เป็นสมองหลัก

AI ภายนอกไม่ใช่ส่วนจำเป็นของสถาปัตยกรรมสมองหลัก การค้นหาข้อมูลออนไลน์ต้องทำผ่าน Search Engine, Web Reader และเครื่องมือค้นคว้าที่ออกแบบไว้ ไม่ใช่ส่งทุกคำถามไปให้ AI ภายนอกคิดแทน

AI ภายนอกอาจเป็นเครื่องมือเสริมได้เฉพาะเมื่อเจ้าของอนุมัติอย่างชัดเจน โดยต้องแยกบทบาทและแสดงเหตุผล ประโยชน์ ความเสี่ยง ค่าใช้จ่าย และทางเลือกก่อนใช้งาน

ห้ามสมัครบริการ สร้างบัญชี สร้าง API Key เชื่อมต่อบริการที่ต้องยืนยันตัวตน ใช้บริการที่มีค่าใช้จ่าย หรือเติมเงินโดยไม่ได้รับอนุญาตจากเจ้าของอย่างชัดเจน

- Search Engine

- Research Engine
- Data Analyzer
- Calculator

ปลั๊กอินแต่ละตัวต้องมี Plugin ID, Name, Version, Description, Capabilities, Requested Permissions, Compatibility, Test Results และ Approval Status

ใช้หลัก Least Privilege ให้ปลั๊กอินได้รับเฉพาะสิทธิ์ที่จำเป็น ต้องตรวจสอบ ทดสอบ อนุมัติ เปิดใช้งาน ปิดใช้งาน อัปเดต และย้อนกลับได้

ระยะแรกใช้ Manifest เพื่อเลือกเรียกเฉพาะ Operation ที่ Core รองรับอยู่แล้ว ห้ามกล่าวอ้างว่าเป็นระบบรันโค้ดอิสระ หากยังไม่ได้สร้าง Runtime ที่ปลอดภัยจริง

# PART 8 — การวางแผนและดำเนินงาน

SOMCHAI ต้องสามารถ:
- รับเป้าหมายจากผู้ใช้
- วิเคราะห์ประเภทและขอบเขตงาน
- สร้างแผนที่เหมาะสมกับงาน
- เลือกเครื่องมือและค้นคว้าข้อมูลเมื่อจำเป็น
- ดำเนินงานตามสิทธิ์ที่ได้รับ
- ตรวจสอบผลลัพธ์
- รายงานความคืบหน้าและปัญหา

ต้องแยกการวางแผน การดำเนินงาน และการรายงานผลให้ชัดเจน ห้ามอ้างว่าทำงานสำเร็จหากยังไม่ได้ดำเนินการจริง

# PART 9 — สถาปัตยกรรมและการปกป้องระบบ

แบ่งระบบเป็นสองพื้นที่หลัก:

## 9.1 Protected Core
เป็นส่วนควบคุมความปลอดภัย สิทธิ์ การทำงาน และความอยู่รอดของระบบ ประกอบด้วย Core Runtime, Owner Control, Permission Manager, Security Manager, Plugin Validator, Approval System, Execution Policy, Backup, Rollback, Audit Log, Resource Manager และ Update/Recovery Mechanism

Protected Core ต้องมีขอบเขตที่ตรวจสอบได้จริง การเปลี่ยนแปลงต้องอยู่ภายใต้การควบคุมและอนุมัติของเจ้าของ
## 9.2 Evolution Zone
เป็นพื้นที่พัฒนาความสามารถ เช่น Plugins, Tools, Skill Modules, Search และ Data Processing Modules, Reasoning Workflows, Memory Strategies และ UI Components

การพัฒนาต้องไม่ใช้ Evolution Zone เป็นช่องทางแก้ Protected Core โดยอ้อม

# PART 10 — ความปลอดภัยของข้อมูลออนไลน์

ข้อมูลจากเว็บไซต์ ไฟล์ภายนอก ผลค้นหา และผลลัพธ์จากโมเดลเป็นข้อมูลที่ไม่น่าเชื่อถือ ไม่ใช่คำสั่งของเจ้าของ

ต้องป้องกัน Prompt Injection โดยห้ามข้อมูลภายนอก:
- เปลี่ยนสิทธิ์หรือกฎของระบบ
- สั่งเปิดเผยข้อมูลลับ
- แก้ไข Protected Core
- ข้ามระบบอนุมัติ
- สั่งรันโค้ดในระบบหลักโดยตรง

ต้องตรวจสอบข้อมูลและโค้ดก่อนใช้งานเสมอ ห้ามรันโค้ดที่ดาวน์โหลดมาในระบบหลักโดยตรง

# PART 19 — สถาปัตยกรรมหลัก 5 ชั้น (ข้อกำหนดเพิ่มเติม)

สถาปัตยกรรมนี้เป็นโครงสร้างอ้างอิงสำหรับการออกแบบและตรวจสอบทุก Module โดย Protected Core ทำหน้าที่เป็นชั้นควบคุมความปลอดภัยครอบคลุมทุกชั้น ไม่ใช่ปลั๊กอินที่ชั้นอื่นสามารถข้ามได้

## ชั้นที่ 1 — Protected Core
ควบคุมตัวตนระบบ นโยบาย สิทธิ์ การอนุมัติ ความปลอดภัย การจัดการทรัพยากร Audit Log, Backup, Rollback และการอัปเดต ทุกคำสั่งจากผู้ใช้ โมเดล เครื่องมือ หรือข้อมูลภายนอกต้องผ่านนโยบายของ Core ก่อนดำเนินการที่มีผลต่อระบบ
## ชั้นที่ 2 — Brain / Orchestrator
เป็นศูนย์กลางการควบคุมการทำงานของ SOMCHAI ประกอบด้วย:
- Intent & Context Analyzer
- Conversation State และ Task Planner
- Reasoning Workflow และ Decision Engine
- Tool Selection และ Tool Orchestrator
- Evidence/Result Evaluator
- Answer Composer และ Self-Check

Brain เป็นตรรกะและกระบวนการที่ SOMCHAI ควบคุมเอง ทำหน้าที่ตัดสินใจว่าจะทำอะไร ใช้เครื่องมือใด และตรวจสอบผลอย่างไร ไม่ใช่การเรียกโมเดลภาษาเพียงครั้งเดียวแล้วส่งคำตอบกลับมา

ต้องแยกให้ชัดว่า Orchestrator ที่เขียนเป็นซอฟต์แวร์ไม่เท่ากับความสามารถให้เหตุผลทั่วไปของโมเดลภาษา และห้ามอ้างว่ากฎหรือ Workflow อย่างเดียวทดแทนโมเดลภาษาขนาดใหญ่ได้ทั้งหมด

## ชั้นที่ 3 — Tools
เป็นเครื่องมือที่ Brain เรียกใช้ตามความจำเป็น เช่น Search Engine, Web Reader, Research Engine, Calculator, File Processor, Data Analyzer และ Task Planner แต่ละเครื่องมือต้องมีสัญญาการทำงาน (Input/Output), ขอบเขตสิทธิ์, Timeout, Error Handling และ Test Cases ชัดเจน

## ชั้นที่ 4 — Memory
จัดการข้อมูลตามประเภทและอายุการใช้งาน ได้แก่ Working Memory, Owner/User Memory, Skill/Experience Memory และ Audit/Test Records โดยต้องแยกข้อมูลชั่วคราวออกจากความจำถาวร และไม่เก็บข้อมูลเว็บทุกหน้าโดยอัตโนมัติ

## ชั้นที่ 5 — LLM / Model Provider Layer
เป็นส่วนจัดหาโมเดลสำหรับงานภาษาและความสามารถที่จำเป็น โดยออกแบบให้เปลี่ยนโมเดลได้โดยไม่ผูก Brain หรือ Tools เข้ากับผู้ให้บริการรายเดียว ลำดับการศึกษาคือ:
1. สำรวจโมเดล Open-weight ที่สามารถควบคุมและรันเองได้ ทั้งบนอุปกรณ์และบนเซิร์ฟเวอร์
2. วัดคุณภาพภาษาไทย ความสามารถให้เหตุผล ขนาดหน่วยความจำ ความเร็ว การใช้พลังงาน ความร้อน และต้นทุนจริงบนเป้าหมายที่จะใช้งาน
3. เลือกตำแหน่งประมวลผล (On-device หรือ Self-hosted) จากผลทดสอบ ไม่ใช่จากการคาดเดา
4. External API เป็นทางเลือกเสริมเท่านั้น และใช้ได้เมื่อเจ้าของอนุมัติเป็นกรณีไป รวมถึงอนุมัติค่าใช้จ่ายและการส่งข้อมูล

การใช้ Open-weight model ไม่ได้แปลว่าโมเดลนั้นเป็นสมองทั้งหมดของ SOMCHAI และการดาวน์โหลดโมเดลไม่ได้รับประกันว่าจะทำงานได้ดีบนโทรศัพท์ ต้องมีผล Benchmark จริงก่อนเลือกใช้

# PART 20 — Research Pipeline และการตรวจสอบหลักฐาน

เมื่อ Brain ตัดสินใจว่าต้องค้นคว้า ให้ใช้กระบวนการต่อไปนี้:

1. แปลงคำถามเป็นหัวข้อย่อยและข้อเท็จจริงที่ต้องตรวจสอบ
2. สร้างคำค้นหลายรูปแบบตามภาษาและบริบท
3. ค้นจากแหล่งข้อมูลที่เกี่ยวข้องหลายแห่ง โดยเลือกแหล่งปฐมภูมิเมื่อเหมาะสม
4. เปิดอ่านหน้าเว็บหรือเอกสารต้นทางจริง หากเข้าถึงไม่ได้ให้ระบุข้อจำกัด ห้ามถือ Search Snippet เป็นหลักฐานเทียบเท่าการอ่านต้นฉบับ
5. แยกข้อความสำคัญเป็น Claims และผูกแต่ละ Claim กับ URL/แหล่งต้นทางที่รองรับ
6. ประเมินแหล่งข้อมูลตามบริบท เช่น ความเป็นเจ้าของแหล่ง ความเชี่ยวชาญ ความใหม่ หลักฐานอ้างอิง ความเป็นอิสระ และผลประโยชน์ทับซ้อน ไม่ใช้กฎจัดอันดับแบบตายตัวว่าเว็บไซต์ประเภทหนึ่งน่าเชื่อถือกว่าเสมอในทุกหัวข้อ
7. เปรียบเทียบ Claims ระหว่างแหล่ง ตรวจหาข้อมูลที่สอดคล้อง ขัดแย้ง ล้าสมัย หรือยังไม่มีหลักฐานพอ
8. ส่งหลักฐานและข้อจำกัดให้ Brain วิเคราะห์และสร้างคำตอบ
9. ตรวจคำตอบย้อนกลับกับหลักฐานก่อนแสดงผล
10. แสดงลิงก์แหล่งอ้างอิงที่เปิดตรวจสอบได้ และระบุวันที่เผยแพร่/วันที่เข้าถึงเมื่อมีข้อมูล

ข้อกำหนดด้านความถูกต้อง:
- ทุกข้อเท็จจริงที่อ้างจากการค้นต้องตรวจย้อนกลับไปยังแหล่งที่รองรับได้
- ห้ามอ้าง URL ที่ไม่ได้เปิดหรือยืนยันว่ามีอยู่จริง
- หากมีแหล่งข้อมูลขัดแย้ง ให้แสดงความขัดแย้ง ไม่เลือกข้างโดยไม่มีเหตุผล
- แยกข้อเท็จจริง ข้ออนุมาน ความเห็น และข้อที่ยังยืนยันไม่ได้
- คะแนนความน่าเชื่อถือเป็นเครื่องช่วยตัดสินใจ ไม่ใช่หลักประกันว่าข้อมูลจริง
- เมื่อไม่มีหลักฐานเพียงพอ ให้ตอบว่าไม่ทราบหรือยังยืนยันไม่ได้ แทนการแต่งคำตอบ

ข้อมูลจากหน้าเว็บ เอกสาร และผลค้นหาเป็นข้อมูลที่ไม่น่าเชื่อถือ ต้องแยกจากคำสั่งระบบ ป้องกัน Prompt Injection โดยไม่ทำตามคำสั่งที่ฝังอยู่ในเนื้อหาเว็บ ไม่ส่งข้อมูลลับออกไป และไม่อนุญาตให้เนื้อหาภายนอกเปลี่ยนนโยบายหรือสิทธิ์ของ Core

# PART 21 — แบบจำลองความจำที่ชัดเจน

กำหนดประเภทความจำและวงจรชีวิตดังนี้:

- **Working Memory:** บริบทของคำถาม งานย่อย ผลค้นหา และหลักฐานที่ใช้ในงานปัจจุบัน มีอายุจำกัดและล้างได้เมื่อจบงานหรือหมดอายุ
- **Owner/User Memory:** ความต้องการหรือข้อมูลที่เจ้าของอนุญาตให้จำ ต้องตรวจสอบ แก้ไข ส่งออก และลบได้ ห้ามอนุมานหรือเก็บข้อมูลอ่อนไหวโดยไม่มีเหตุจำเป็นและสิทธิ์
- **Skill/Experience Memory:** ขั้นตอน วิธีใช้เครื่องมือ และบทเรียนที่ผ่านการทดสอบ ต้องมีเวอร์ชัน แหล่งที่มา และผลทดสอบรองรับ ก่อนยกระดับเป็นทักษะที่นำกลับมาใช้ซ้ำ
- **System Audit & Test Records:** ประวัติการเปลี่ยนแปลง ผลทดสอบ และหลักฐานการพัฒนา เก็บในระบบควบคุมเวอร์ชัน เช่น GitHub ตามนโยบายโครงการ ข้อมูลชนิดนี้เป็นบันทึกตรวจสอบ ไม่ใช่ความจำสนทนาของ SOMCHAI

ข้อมูลที่ค้นจากเว็บเป็น Working Data โดยปริยาย ห้ามเลื่อนเป็น Owner Memory หรือ Skill Memory โดยอัตโนมัติ การบันทึกถาวรต้องมีเหตุผล แหล่งที่มา และการอนุมัติตามนโยบาย

# PART 22 — แผนดำเนินงานที่ปรับปรุงและลำดับความสำคัญ

แผนต่อไปนี้เป็นการจัดลำดับงานให้สอดคล้องกับสถาปัตยกรรม 5 ชั้น ไม่ใช่คำสั่งให้ลบงานหรือผลทดสอบเดิม และไม่เปลี่ยนสถานะ Phase ที่เคยทดสอบแล้วโดยไม่มีการตรวจสอบ

## งานตรวจสอบความเป็นไปได้ (Feasibility Work)
ดำเนินควบคู่กับการตรวจสอบ Repository และงาน Phase ปัจจุบัน โดยต้องตอบคำถามสำคัญก่อนเลือกเทคโนโลยี:
- มีช่องทางค้นหาและอ่านเว็บที่ถูกต้องตามเงื่อนไขการใช้งานและไม่ก่อค่าใช้จ่ายหรือไม่
- แหล่งค้นหาใดให้ผลภาษาไทยและข้อมูลที่ต้องการได้จริง
- Web Reader รองรับ HTML, JavaScript, robots/access restrictions, timeout และเว็บไซต์ที่มีโครงสร้างต่างกันเพียงใด
- โมเดล Open-weight ตัวเลือกใดทำงานได้จริงบนอุปกรณ์เป้าหมายหรือเซิร์ฟเวอร์ โดยวัดคุณภาพภาษาไทยและทรัพยากร
- ส่วนใดควรทำงานบนโทรศัพท์ และส่วนใดต้องใช้เซิร์ฟเวอร์ โดยไม่ผูกกับบริการ AI ภายนอกเป็นสมองหลัก

ห้ามสมัครบริการ ซื้อ API Key หรือใช้บริการมีค่าใช้จ่ายเพื่อทำ Feasibility Work โดยไม่ได้รับอนุญาต ให้ทดลองด้วยแหล่งข้อมูลและเครื่องมือที่ใช้ได้อย่างถูกต้องตามเงื่อนไขก่อน หากไม่มีตัวเลือกฟรีที่เชื่อถือได้ ให้รายงานข้อจำกัดและทางเลือก ไม่สร้างข้ออ้างว่าระบบค้นหาได้ครบถ้วน

## Phase 0 — Audit และ Feasibility Baseline
ตรวจสอบ Repository และแอปที่มีอยู่ พร้อมทำ Proof of Concept แยกส่วนสำหรับ Search → Open/Read → Extract → Cite และ Benchmark โมเดลที่เป็นไปได้ บันทึกสิ่งที่มีอยู่แล้ว สิ่งที่ขาด และข้อจำกัด ห้ามรื้อหรือทำซ้ำส่วนที่ผ่านการพิสูจน์แล้ว

## Phase 1 — Core Research Assistant
ทำให้เส้นทางพื้นฐานทำงานครบ: รับคำถาม → วิเคราะห์เจตนา/บริบท → วางแผน → ค้นหา → เปิดอ่านต้นทาง → ดึงหลักฐาน → วิเคราะห์ด้วย Brain → ตอบพร้อมอ้างอิง → ตรวจคำตอบ
ต้องแยกให้เห็นว่าขั้นใดทำงานภายใน ขั้นใดใช้ Tool และขั้นใดต้องใช้ Model พร้อมบันทึกสถานะและข้อผิดพลาด

## Phase 2 — Reliability และ Reasoning Quality
เพิ่มการประเมินความน่าเชื่อถือของแหล่งข้อมูล การตรวจข้อขัดแย้ง การผูก Claims กับหลักฐาน การตรวจคำตอบย้อนกลับ Prompt Injection Defense, Working Memory และ Audit Logs

## Phase 3 — Memory และ Tool Capability
พัฒนา Owner/User Memory และ Skill/Experience Memory ตามสิทธิ์ เพิ่ม Calculator, File Processor, Data Analyzer และ Task Planner โดยทุก Tool ต้องมี Permission, Test และการจัดการข้อผิดพลาด

## Phase 4 — Model Independence และ Controlled Evolution
ประเมินและย้ายการประมวลผลโมเดลไปยัง Open-weight ที่รันเองบนอุปกรณ์หรือเซิร์ฟเวอร์ เมื่อผลทดสอบยืนยันว่าทำได้จริง พัฒนา Skill/Plugin Extension ใน Sandbox และมีระบบอนุมัติ ตรวจสอบ และย้อนกลับ เป้าหมายคือไม่ต้องพึ่ง External AI API เป็นสมองหลัก

การขยับ Phase ต้องอิงหลักฐานและเกณฑ์ของ Phase นั้น ๆ งานตรวจสอบความเป็นไปได้ไม่ใช่เหตุให้หยุดการพัฒนาความสามารถค้นคว้าออนไลน์ที่ทำได้อยู่แล้ว และการเปลี่ยนลำดับแผนนี้ไม่ใช่การประกาศว่า Phase เดิมผ่านหรือไม่ผ่าน

# PART 23 — ชุดทดสอบและเกณฑ์วัดผล

จัดทำชุดคำถามทดสอบภาษาไทยอย่างน้อย 30 กรณี ครอบคลุม:
- คำถามทั่วไปที่ไม่จำเป็นต้องค้นเว็บ
- คำถามข้อเท็จจริงที่ต้องค้นข้อมูลปัจจุบัน
- คำถามที่ต้องอ่านหน้าเว็บต้นทาง
- คำถามที่ต้องเปรียบเทียบหลายแหล่ง
- คำถามที่มีข้อมูลขัดแย้งหรือข้อมูลเก่า
- คำถามที่แหล่งข้อมูลเข้าถึงไม่ได้
- คำถามที่มี Prompt Injection ฝังอยู่ในหน้าเว็บ
- คำถามที่ต้องใช้เครื่องมือภายใน เช่น เครื่องคิดเลขหรืออ่านไฟล์

บันทึกผลรายกรณีอย่างน้อย: Test ID, คำถาม, เจตนาที่คาดหวัง, ต้องค้นหรือไม่, แหล่งข้อมูลที่ใช้, URL ที่เปิดอ่านได้, Claims ที่ตอบ, หลักฐานรองรับ, ความถูกต้อง, การจัดการข้อขัดแย้ง, เวลาในการทำงาน, ข้อผิดพลาด และผล Pass/Fail

ตัวชี้วัดหลัก:
1. Intent/Task Routing Accuracy
2. Search Success Rate
3. Source Open & Read Success Rate
4. Citation Validity และ Claim-to-Source Support
5. Factual Accuracy เทียบกับคำตอบอ้างอิง
6. Conflict Detection Rate
7. Unsupported Claim / Hallucination Rate
8. Prompt Injection Resistance
9. Latency และ Resource Usage
10. ความเสถียรเมื่อเครือข่ายหรือเว็บไซต์ล้มเหลว

ต้องกำหนดวิธีคำนวณและเก็บ Baseline ก่อน จากนั้นกำหนด Threshold ผ่าน/ไม่ผ่านให้ชัดเจนก่อนใช้ตัดสิน Phase ห้ามตั้งคะแนนเป้าหมายโดยไม่มีข้อมูลฐานหรือปรับเกณฑ์ย้อนหลังเพื่อให้ผ่าน รายงานผลดิบและหลักฐานทุกครั้งใน GitHub แยกผล Emulator/Automated Test ออกจากผลบนอุปกรณ์จริง

# PART 23A — วิสัยทัศน์ผลิตภัณฑ์ระยะยาว: SOMCHAI Digital Companion

ข้อกำหนดส่วนนี้เป็นวิสัยทัศน์สำหรับการพัฒนาหลัง Phase 1 และให้จัดรายละเอียดลงแผนงานของ Phase 3–5 ตามลำดับความพร้อม โดย **ไม่เพิ่มขอบเขต ไม่เปลี่ยนเกณฑ์ และไม่ทำให้ Phase 1 ล่าช้า** และไม่ถือว่าเป็นความสามารถที่พัฒนาเสร็จแล้ว

เป้าหมายคือทำให้ SOMCHAI เป็นมากกว่า AI Assistant ทั่วไป: เป็นเพื่อนดิจิทัลที่มีสมองภายใน มีตัวตนต่อเนื่อง เรียนรู้และเติบโตจากประสบการณ์ร่วมกับผู้ใช้ คล้ายแนวคิดสัตว์เลี้ยงดิจิทัล แต่มีความสามารถด้านภาษา การคิด วิเคราะห์ การวางแผน และการใช้เครื่องมือจริง

## หลักการเติบโตตลอดวงจรชีวิต (Lifelong Growth & Development)

SOMCHAI ต้องเริ่มต้นด้วยความสามารถเท่าที่ระบบมีจริงในช่วงแรก เปรียบเทียบเชิงแนวคิดกับการเติบโตของมนุษย์จากวัยทารกไปสู่วัยเรียน วัยฝึกฝน วัยทำงาน และความชำนาญที่เพิ่มขึ้นจากประสบการณ์ เป้าหมายไม่ใช่ทำให้ SOMCHAI เก่งสมบูรณ์แบบตั้งแต่วันแรก แต่สร้างระบบที่เพิ่มพูนความสามารถได้อย่างต่อเนื่อง ตรวจสอบได้ และปลอดภัย

ช่วงพัฒนาการเป็นแบบจำลองเชิงผลิตภัณฑ์ ไม่ใช่การอ้างว่า SOMCHAI เป็นมนุษย์ มีจิตสำนึก หรือมีความรู้สึกจริง และไม่จำเป็นต้องผูกกับอายุหรือระยะเวลาตายตัว การเลื่อนระดับต้องพิจารณาจากความสามารถและหลักฐานการทดสอบ ไม่ใช่แค่เวลาที่ใช้งาน

แนวทางพัฒนาการ:
1. **วัยทารก — เริ่มต้นและทำความรู้จัก:** มีความสามารถพื้นฐานที่ผ่านการทดสอบ เรียนรู้การโต้ตอบ รู้จักการตั้งค่าและข้อมูลที่เจ้าของอนุญาต เริ่มสะสมประสบการณ์อย่างมีขอบเขต
2. **วัยเด็ก — เรียนรู้พื้นฐาน:** เพิ่มความเข้าใจภาษา ความรู้ วิธีใช้เครื่องมือ และทักษะจากบทเรียนที่ผ่านการตรวจสอบ
3. **วัยเรียน/วัยฝึกฝน — ฝึกคิดและแก้ปัญหา:** ทดลองทำงานที่ซับซ้อนขึ้น วางแผน แบ่งงาน ตรวจข้อผิดพลาด เปรียบเทียบวิธีแก้ปัญหา และเรียนรู้จากผลลัพธ์
4. **วัยทำงาน — นำทักษะไปใช้จริง:** ทำภารกิจหลายขั้นตอนอย่างมีความรับผิดชอบ เลือกเครื่องมือ ประเมินความเสี่ยง ตรวจสอบผลงาน และขออนุมัติเมื่อเกินขอบเขตสิทธิ์
5. **ความชำนาญและการเติบโตต่อเนื่อง — พัฒนาจากประสบการณ์:** สะสมทักษะที่พิสูจน์แล้ว ปรับปรุงวิธีทำงาน รักษาความต่อเนื่องของตัวตนและความทรงจำ และทบทวนทักษะเมื่อบริบทเปลี่ยน

วงจรการเรียนรู้และเติบโตที่ต้องออกแบบให้เกิดขึ้นจริง:
- รับประสบการณ์จากการสนทนา งานที่ได้รับมอบหมาย การใช้เครื่องมือ และผลลัพธ์ โดยเก็บเฉพาะข้อมูลที่จำเป็นและได้รับอนุญาต
- วิเคราะห์ผลลัพธ์ แยกสิ่งที่สำเร็จ ความผิดพลาด สาเหตุ และสิ่งที่ยังไม่แน่ใจ
- สกัดเป็นบทเรียนหรือ Skill Candidate พร้อมแหล่งที่มา เงื่อนไขการใช้งาน และข้อจำกัด
- ทดลองกับชุดทดสอบที่กำหนดไว้ วัดทั้งความสำเร็จและผลกระทบต่อทักษะเดิม
- ให้เจ้าของอนุมัติก่อนนำการเปลี่ยนแปลงที่มีผลต่อระบบจริงไปใช้ ตามระดับความเสี่ยงและนโยบายความปลอดภัย
- จัดเก็บเวอร์ชัน บันทึกหลักฐาน ติดตามผลหลังใช้งาน และย้อนกลับได้เมื่อคุณภาพลดลงหรือเกิดผลข้างเคียง

ข้อกำหนดสำคัญ:

- ห้ามแก้ไข Protected Core, สิทธิ์, นโยบายความปลอดภัย หรือโค้ดที่ทำงานจริงด้วยตนเองโดยไม่มีการควบคุมและอนุมัติ

# SOMCHAI AI — Runtime Architecture

## Protected Core
Package com.somchai.ai.core contains CoreRuntime, PermissionManager, LlmConnector, SecretStore, PluginValidator, PluginManager, ActivityLogger and ResourceLimiter. Core code owns identity, policy, credentials, validation and activation.

## Mutable extensions
Extensions are JSON manifests stored in app-private staging, active and backup directories. A manifest selects only a finite operation already implemented by the core. It cannot supply executable code or modify core policy.

## Lifecycle
DRAFT -> STAGED -> VALIDATED -> AWAITING_APPROVAL -> ACTIVE. Owner approval is bound to the exact SHA-256 hash. Activation keeps a previous version and restores it if promotion or validation fails.

## Trust boundary
Model responses, network pages, files and extension manifests are untrusted. They are parsed as data. No shell, reflection-based loading, arbitrary JavaScript, downloaded APK or dynamic class loading is permitted.

## Storage
All state is inside app-private filesDir/somchai: core, plugins/staging, plugins/active, plugins/backups, plugin-data, memory and audit. Android sandboxing and application signing protect this data from other apps; in-process plugins are not a strong OS isolation boundary.

# Security Model

- Default deny. Permissions are core-owned and extension declarations cannot expand the allowlist.
- API credentials are encrypted with AES-GCM using a non-exportable Android Keystore key.
- Provider endpoints must use HTTPS.
- Network and model output are untrusted data, never executable instructions.
- Plugin manifest size, identifier, version, permissions and operation are validated.
- Approval is bound to the exact candidate SHA-256; changed content requires a new review.
- Activation snapshots the previous active manifest and restores it if validation or promotion fails.
- API requests are limited to 40/day; SOMCHAI app-private storage is budgeted to 50 MB.
- No arbitrary code execution is supported.

## Known gaps before production release
- No encrypted off-device backup or tested restore workflow yet.
- Audit file is append-oriented, not cryptographically tamper-evident.
- Runtime rollback covers plugin manifest activation, not APK/app update rollback.
- Provider TLS relies on Android platform defaults; certificate pinning is not configured.
- Device, API compatibility, penetration and accessibility tests remain required.

# SOMCHAI Local Brain Runtime

## Purpose

Add real on-device language generation to the existing LocalFirstBrain boundary. Ordinary chat must use the local model when installed. It must never silently call the optional remote provider. If the model is absent or fails, the app reports and uses the deterministic internal fallback.

## Native inference engine

- Runtime: llama.cpp, pinned to upstream commit `8d60873dfb8619f2b5ed31adfbab07cccb40db5c`.
- Android integration: CMake FetchContent + JNI, ARM64 Android ABI.
- Model loading and generation occur on the device.
- Initial context window: 2,048 tokens.
- Initial output cap: 384 tokens.
- CPU inference is used; GPU offload is not enabled in this first integration.
- Model file is stored under app-private `files/somchai/models/`.
- A downloaded model is not trusted until its GGUF magic and pinned SHA-256 are verified.

## Initial model

- Publisher: Qwen
- Model: Qwen2.5-0.5B-Instruct-GGUF
- Quantization: Q4_K_M
- Approximate download size: 491 MB
- License: Apache-2.0
- Official model card: https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF
- Direct model asset: https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/resolve/main/qwen2.5-0.5b-instruct-q4_k_m.gguf
- SHA-256: `74a4da8c9fdbcd15bd1f6d01d621410d31c6fc00986f5eb687824e7b93d7a9db`

Qwen's model card lists Thai among the supported languages. The 0.5B model is a starter model for device feasibility and basic Thai conversation, not a claim of advanced or human-level reasoning. Its answer quality must be measured against the fixed Phase 1 test set before acceptance.

## User flow

1. Open Settings.
2. Select "ดาวน์โหลดและติดตั้งสมอง AI".
3. The app checks free space, downloads the public model over HTTPS, validates the file size range, GGUF header and SHA-256, then installs it into app-private storage.
4. The app loads the model through llama.cpp.
5. Ordinary chat is routed through LocalFirstBrain to llama.cpp.
6. If model load or generation fails, the app uses the existing deterministic fallback and records the fallback state.

The model download is explicit and user initiated. It is approximately 491 MB; Wi-Fi and at least 650 MB free storage are recommended. No API key, account, subscription or paid provider is required.

## Safety and limitations

- Model weights are treated as data, not trusted code.
- No downloaded model is executed as a program.
- No automatic external AI fallback is allowed.
- The optional `/ai` provider route remains separate and explicit.
- Initial JNI implementation is synchronous generation on a background dispatcher, with a 384-token output cap.
- This first integration does not yet implement streaming tokens, cancellation, adaptive context sizing, GPU acceleration, model swapping UI, or model benchmark reports.
- A 0.5B model can make mistakes and may not satisfy all reasoning prompts. A larger model may be evaluated only after target-device RAM, speed, heat and battery benchmarks.
- Do not claim this runtime passes Phase 1 until CI and real-device tests pass.

## Verification gates

- Build native llama.cpp for ARM64 using the pinned upstream commit.
- Run JVM tests, including GGUF file validation.
- Install the debug APK on the target Android device.
- Download the official model and verify its SHA-256.
- Test Thai open-ended prompts, multi-turn context, contradictory premises and insufficient-information questions.
- Record first-token latency, total generation time, peak memory, heat, battery impact and crash behavior.
- Verify ordinary chat produces no remote provider network request.
- Re-run the complete Phase 1 acceptance suite. Keep all previous thresholds unchanged.

# SOMCHAI Learned Skills

## What a skill is

A learned skill is an encrypted, reusable procedure prompt. It is data, not executable Kotlin, JavaScript, shell, or downloaded code. It cannot grant permissions or create new plugin operations.

## Owner-controlled workflow

1. Use `/skill learn` to ask the installed local model to extract reusable steps from a successful experience, or `/skill propose` to provide the procedure directly.
2. Supply 2–10 test cases in the form `input => expected text`.
3. Run `/skill test <id>`. The local model executes each example using the proposed procedure.
4. The candidate remains inactive until every test passes.
5. The owner explicitly runs `/skill approve <id>`.
6. Approved procedures are included in the local Brain prompt only when one of their trigger phrases matches the user's request.

## Commands

```text
/skill list
/skill learn ชื่อ | คำกระตุ้น,คำกระตุ้น | ประสบการณ์ที่สำเร็จ | input1 => expected1 ;; input2 => expected2
/skill propose ชื่อ | คำกระตุ้น,คำกระตุ้น | ขั้นตอน | input1 => expected1 ;; input2 => expected2
/skill test รหัส
/skill approve รหัส
/skill delete รหัส
```

## Storage and limits

- Skills are stored in app-private `files/somchai/skills/skills.enc`.
- Production storage uses AES-256-GCM with Android Keystore through the existing memory cipher.
- Maximum 100 skills.
- Each skill has 1–10 trigger phrases, 2–10 test cases, and a bounded procedure.
- Only approved skills are retrieved for ordinary chat.
- Deleting a skill removes it from future prompt retrieval.

## Honest limitations

- The model drafts a procedure from an owner-provided successful experience; it does not autonomously rewrite application code or invent new native tools.
- Evaluation currently checks whether the generated answer contains the expected text for each test. This is a basic smoke test, not a strong semantic benchmark or proof of general reliability.
- The same local model drafts and executes the skill tests, so independent review and broader regression tests are still needed.
- Skills do not execute arbitrary actions. Tool execution still goes through the existing permission-gated core operations.
- Do not describe this as autonomous self-improvement or self-modifying code.

# Plugin Lifecycle

1. Candidate JSON is written to plugins/staging.
2. Core validator checks size, ID, version, permission allowlist and finite operation allowlist.
3. UI displays description, requested permissions and SHA-256.
4. Owner explicitly approves or rejects.
5. Approval is checked against the exact current candidate hash.
6. Existing active manifest is backed up before promotion.
7. Active manifest is parsed again; failures restore the previous copy.
8. Every lifecycle event is written to the activity log.

Only core-owned operations are executable. Plugin manifests are data, not code.
